## 内存占用测量与优化（凌晨 07:2x–07:4x）

### 结论

标题界面（**还没进关卡**）稳定 RSS **666 MB** → 调优后 **583 MB（−12.5%）**，
Private_Dirty 588 → 506 MB，VSZ 8176 → 1331 MB，线程 106 → 50。
**画面与音频判据零回归**（`redirect external bind`=3、`Silent mode`=0、`Enqueue`=217、判活九项全 0）。
优化**全是 4 个环境变量**，零代码改动、零性能退化（日志吞吐 78 237 → 78 775 行，持平）。

### 🔴 意外发现：容器不是原生 aarch64

`uname -m` 报 `aarch64`，但 `/proc/cpuinfo` 是 **AMD Ryzen 9 7950X**、宿主 `docker info` 是 **x86_64**、
`ps` 里每条命令都长成 `/usr/bin/qemu-aarch64 <binary>`、`nproc=32`。
⇒ **容器 = x86_64 宿主 + aarch64 用户态模拟**。这直接影响内存判读：

| 容器特有开销 | 大小 | 掌机 |
|---|---|---|
| qemu 翻译缓存（`rwxp` 匿名段，宿主地址） | **128 MB** | 不存在 |
| llvmpipe（`libLLVM-12` 36.5 + `swrast_dri` 10.9） | **~47 MB** | 用 Mali 真 GPU |

⇒ 掌机等效 ≈ **408 MB**（粗估）。`nproc=32` 还导致 llvmpipe 起 32 线程、glibc arena 上限 8×32。

### 分解（按 RSS 聚合 smaps）

匿名 **590 MB**（占 85.6%）→ 其中 qemu `rwxp` 128 MB；其余是堆/arena/大块分配。
文件映射里只有 llvmpipe 的 LLVM(36.5)+swrast(10.9) 可观；`global-metadata.dat` 7.0 MB；loader 5.7 MB。

### 实测 A/B（同二进制，仅 env 不同，各 32 s）

| 组 | RSS | PrivDirty | 线程 |
|---|---|---|---|
| 基线 ×2 | 665 / 666 | 588 / 589 | 106 |
| `MALLOC_ARENA_MAX=2` | 663 | — | 106 |
| `MALLOC_ARENA_MAX=1` ×3 | 616 / 622 / 616 | 538 / 544 | 106 |
| `LP_NUM_THREADS=2` | 635 | 558 | **50** |
| `ARENA_MAX=2` + trim 阈值 | 609 | 532 | 106 |
| `ARENA_MAX=1` + trim 阈值 | 605 | 521 | 106 |
| **`ARENA_MAX=2`+trim+`LP_NUM_THREADS=2`（采用）** | **583** | **506** | **50** |

### 两条被实测推翻的直觉（值得记）

1. **「arena 段数多」≠「RSS 高」**：基线有 **101 个 64 MB 对齐的匿名段**，看上去触目惊心；
   但 `MALLOC_ARENA_MAX=2` 把段数压到 **1**，RSS 只降 **3 MB** —— 那些段绝大多数是**空的虚拟预留**。
   ⇒ 别数段，只看 RSS / Private_Dirty。真正干活的是 **trim 阈值**（配 arena=2 就降 57 MB）。
2. **判可裁剪性不能看文件大小**：`libavcodec` 链着 `librsvg`(9 MB 文件) → `libicuuc/libicudata`(27 MB)、
   `libcodec2`(14 MB)，看着能省 50 MB；**按 RSS 看 `librsvg` 只有 1.9 MB、`libicuuc` 0.5 MB、
   `libicudata` 连 top25 都没进**（共享库，页在多进程间共享）。⇒ 裁这些收益远小于调优。

## 第四轮（11:00–11:20）音频混音器：视频无声 + 音量键无效 —— 一个缺陷的两个侧面

**用户报告**：① 开场视频没声音；② 视频结束后界面音乐极大，掌机音量降到 0 也不变。
**要求**：查日志；**后续不要主动在掌机上启动游戏**（故本轮只在容器跑测 + 只读掌机）。

### 真机只读取证（关键）

```
/sys/class/power_supply/axp2202-battery/openbor_volume = 0      ← 音量键写的就是它
amixer digital volume = 63/63 (100%)、lineout volume = 31/31    ← 硬件 DA 满量程
grep -rl openbor_volume /mnt/vendor/bin ⇒ dmenu.bin / portsCtrl.dge / 各模拟器 .dge
```

⇒ 这台固件的音量模型 = **硬件满量程 + 应用自己读 `openbor_volume` 缩放 PCM**。
任何不读该值的程序都是满音量、按键无效。我们读了（`volume backend=sysfs … percent=0 keys=1`）
但**只在 FMOD 路径用**，而 Wwise 路径零缩放。

### 根因（两条，全在 port 侧）

1. **`fakefmod.cpp` 在 Wwise 抢占 writer slot 后 `continue`，永不调 `fmodProcess()`。**
   那是 Unity **整个音频系统唯一的 pull 接口** ⇒ Unity 混音器静止。
   `VideoPlayer.audioOutputMode` 默认 `AudioSource` ⇒ **视频音轨走这条路 ⇒ 没声音**。
   佐证（非推测）：日志 `android/media/AudioTrack` **0 次**；`libunity.so` dynsym 无
   `AudioTrack`/`libmedia`/`AAudio` UND 符号 ⇒ 排除 Direct 模式。
2. **`opensles.cpp::BufQ_Enqueue` 直推 `SDL_QueueAudio`，零增益** ⇒ Wwise 音乐满量程、音量键无效。

### 修法

`audio_bus` 从"设备登记处"升级为**软件混音器**：`bd_audio_bus_push(owner, pcm, n)` 各写自己的 ring，
`bd_audio_bus_pump(dev)` 逐样本相加 + 饱和 + **统一施加系统增益** + 补 SDL 队列。
队列水位 75 ms（`BD_AUDIO_QUEUE_MS`）；ring 各 1 s 上限（落后丢最老）；pump 由两个生产者线程各自调
（锁保护）。Wwise refill 判据从"SDL 队列深度"改为"自己 ring 深度"，且单 tick 内循环 refill。

**顺带修两处设备生命周期 bug（本轮未触发，防御性）**：`Play_SetPlayState` 的暂停分支与
`Object_Destroy` 原本无条件 `SDL_PauseAudioDevice/CloseAudioDevice` —— 会**关掉借来的 FMOD 设备**，
连视频音轨一起弄死。新增 `PlayerState::owns_device` 区分。

⇒ **Unity 真的调用了 `Activity.finish()`（= 退出应用）**，只因桩是空实现才没真退。

  **loader 侧能产生 111 的只有 `guide` 项**（`g_button_remap` 里唯一值 111）；不产生 4。
  ⇒ 推理收敛：**某个 SDL 按钮被报成 GUIDE ⇒ remap 成 ESCAPE ⇒ Unity finish()**。
- `[BD-MISS]` 里 `finish` 的 8 条是**连续的方法签名解析日志**（遍历父类同名方法），不是 8 次调用 —— 别看错。

`Tutorial Played`(192987/193278/232237) + `controllerType: GameController` 成对 → `Tutorial Stopped`(221916) → 退出。
⚠️ 上述 NRE / 银行加载失败 / 音频溢出**与按键无关**，是后续待查项。

**可复用手法**：想知道"游戏请求了什么系统能力"，除了 `[BD-*]` 标签，还要看
**`[JNIVM]: [STUB-MISS] ... returning default`** —— 那是**游戏侧调用未被桩实现的方法**的直接记录，
比从 loader 侧反推快得多。（jnivm 缓存解析结果 ⇒ 同一条只出现一次，别据此判断调用次数。）

## 18:20 按键问题定案：`guide = "ESCAPE"` × **InControl** 的 Back

### 用户现象与澄清（两轮口径）
① 关卡内按 ABXY/Start/Select/Guide 都像"返回"（不是退出进程）；② 后又描述为：按这些键会**先**弹出
「是否退出游戏？」，此时按 B 会关掉弹窗**并**触发跳跃；③ 对比：**Samurai2 / Maximus2 按键完全正常**。
⇒ 前提修正：**不是映射表错位**（先前"controller_name 拼写 / SDL 两段式编号导致整表错位"两个假设**都被证伪**）。

### 硬证据（真机 log.txt + 本地探针）
- 真机日志（诊断版，20.4 万行）`[BD-PAD]` **83 行**，全部按键的 keycode **都正确**：
  A=96 / B=97 / X=99 / Y=100 / Start=108 / Select=109 / D-pad=19–22；
  **`kc=111`（ESCAPE）在整个日志里只由 `btn=5 (guide)` 产生过**（两行，两次按下）。
- 时间对齐（**决定性**）：
  `188437 [BD-PAD] DOWN btn=5 (guide) kc=111` → `188457 Unity: Fade Out`（相隔 20 行）。
  同一次运行里游戏侧 `Fade Out` **只出现 1 次**，且 A/B/X/Y/Start/Select 那些按下**前后没有任何游戏侧反应**。
  ⇒ **弹窗只由 guide 唤起**；用户"都触发"的印象来自"弹窗起来后任意键都在和弹窗交互"。
- `[BD-PAD-MAP]` dump：`remap[sdl btn 5] -> android keycode 111`；`guide <- joy button 8`；
  物理 guide 的内核码是 **BTN_TL2(312)**（探针配对：`CBUTTON button=5 name=guide / EVDEV 312`，
  且同一按还会多报一个 **KEY_GOTO(354)** —— 那是固件"菜单"键，SDL 里落到无绑定的 raw btn 11，不影响）。
- **游戏为什么吃 ESC**：metadata 里整片 `InControl.UnityDeviceProfiles.*`（含 `Xbox360AndroidUnityProfile`），
  日志第 1159 行 `InControl (version 1.8.6 build 9370)` ⇒ Oddmar 走 **InControl**。
  InControl 的 Android/Xbox profile 把 **`Back` → `KeyCode.Escape`**（Android 上 Back 就是 ESC）。
  ESC 进 Unity = `KeyCode.Escape` = 框架级 Back ⇒ 弹退出确认。
  **这就是"为什么只有 Oddmar"**：只有它套了 InControl 这层抽象；Samurai2/Maximus2 直接把 Escape 当普通键忽略。
- 顺带确认 Unity 的 Android→JoystickButton 映射：A=96→JB0、B=97→JB1、X=99→JB2、Y=100→JB3、
  L1=102→JB4、R1=103→JB5、START=108→JB10、SELECT=109→JB11 —— 与 InControl 的 Android profile
  （Action1..4=Button0..3、Start=Button10、Select=Button11）**逐项吻合**，所以"Start 反应是对的"成立。

### 修法（本轮已落）
- `platform/common/input_backend.cpp::parse_keycode_name()` 补全 keycode 词汇：`BUTTON_C` / `BUTTON_Z` /
  **`BUTTON_MODE`**(110) / `BUTTON_L3` / `BUTTON_R3`。
  ⚠️ 此前 `BUTTON_MODE` **不在名字表里** ⇒ 写进 toml 会被 `bind()` 静默忽略（kc=-1），
  不过正好会回落到 `toAndroidKeycode()` 的 default（GUIDE→KEYCODE_BUTTON_MODE）——**是巧合，别依赖**。
- toml（掌机 `unity.toml` + staging 两份）`guide = "ESCAPE"` → **`guide = "BUTTON_MODE"`**。
- ⚠️ **`guide = "ESCAPE"` 是全部 port 的模板默认值**（5 个 stage + 4 个 configs 都有）。别的游戏暂不动
  （实测无害），但**新接 InControl / 会用 Escape 当 Back 的游戏必须改**。

### 可复用手法
- **"某个键进了游戏变成别的语义" ⇒ 先分清三跳**：① 内核 evdev 码 → ② SDL 逻辑按钮（看
  `PAD-MAP` 的 `GetBindForButton` dump）→ ③ loader 注入的 Android keycode（看 `[BD-PAD] kc=`）。
  **只查第三跳的配置往往不够**，还要问"游戏用什么输入框架"（Unity 原生 / InControl / Rewired …）。
- **找游戏帧里的输入框架**：`strings global-metadata.dat | grep -E "^InControl\."`；
  日志里框架会自报版本（`InControl (version 1.8.6 build 9370)`）。
- **对齐"按键 → 游戏反应"最省力的锚点**：游戏侧 `[BD-ANDROID] Unity:` 日志行号（本轮 `Fade Out` 一击命中）。
