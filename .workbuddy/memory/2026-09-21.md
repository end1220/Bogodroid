## 踩到的坑（重要，可复用）

1. **`bogo-builder:unity2017-armv7` 缺 arm64 FFmpeg dev**：`CMakeLists.txt:98`
   `pkg_check_modules(FFMPEG REQUIRED ...)` 直接失败。Debian 11 已过 LTS，
   `deb.debian.org/debian-security` 上 ffmpeg 包全 404；换 `archive.debian.org`
   又因为归档 amd64 索引比镜像内安全更新版本旧，**apt 会为了解依赖卸载
   `cmake`/`libsdl2-dev`/`libwayland-dev`**（`apt-get install -s` 可预演）。
   → 结论：本仓库近期端口**不是**用 Debian 交叉工具链编的，而是在
   aarch64 Ubuntu 20.04 容器里**原生**编（既有 `unityloader.release.log` 的
   `.comment` 是 `GCC 9.4.0-1ubuntu1~20.04.2`）。见 `_results/` 记录。
2. **`GlES_Dev` 镜像 ≠ 容器**：`dropbeak-gles-dev:local` 里**没有** g++/cmake/ninja，
   工具链只存在于 `GlES_Dev` 容器可写层。新建容器编译会 `g++: command not found`。
   → 直接用 `GlES_Dev`，源码用 tar + `docker cp` 同步进 `/workspace/Bogodroid`。
3. **`docker cp` 的 Windows 路径**：Git Bash 里 `tar -czf "D:/..."` 会被当成远程主机
   （`Cannot connect to D:`），要用相对路径或 `--force-local`；`docker cp` 则**必须**
   绝对 Windows 路径。
4. **`pkill -f Xvfb` 会杀掉自己**：`docker exec bash -c '...pkill -f Xvfb...'` 的命令行
   本身含 "Xvfb" → 自杀，表现为脚本 4 秒就结束且无输出。用 `pkill -x`。
5. **本机 bash 的 PATH 缺 `/usr/bin`**：每条 Bash 调用前需
   `export PATH="/usr/bin:/bin:$PATH"`，否则 `mkdir/ls/grep` 全 not found。
6. **Release 的 LTO 串行**：ninja 下 `-flto` 无 jobserver → `ltrans` 串行，链接 ~10 min
   （playbook §7 已提过）。要快就 `-DCMAKE_BUILD_TYPE=RelWithDebInfo`（不带 LTO）。
   带 `-g` 的构建才能 `addr2line` 定位 `[BD-SEGV]` 帧。

# 2026-09-21（下半场）— 崩溃根因定位并修复；已从 SEGV 推进到「干净退出」

## 更正上一节结论

上面的「故障 PC 落在 libunity + 0x319984」和「缺失桩把异常升级成 libunity 空指针」
**都是错的**。详见 [`docs/CASE_STUDIES.md`](../docs/CASE_STUDIES.md) 案例四。要点：

- `[SIGNALS] sigaction 11 ...` 显示 **Unity 的 `libunity` JNI_OnLoad 会抢 SIGSEGV**
  （handler = `libunity+0x3196bc`，覆盖 `main()` 早先装的 `segfault_handler()`），
  然后**链式回调**旧 handler。`libunity+0x319b2c` 就是那个链式跳板。
- 该 handler 把 TLS 基址放进 `x29`（`mrs x29, tpidr_el0`）→ glibc 走 frame pointer 的
  `backtrace(3)` 读到 TLS 内存 → 吐出**假帧**。`0x319984` 只是 `bl 0x319b2c` 的返回地址。
- 真因：`std::rethrow_exception` 收到**空 `exception_ptr`** →
  libstdc++ 读异常对象下方 0x80 字节 → `si_addr=0xffffffffffffff80`（= -0x80）。
  调用点在 `libjnivm/include/jnivm/method.h`（`j2invoke` 尾部）与 `vm.cpp`（`ExceptionDescribe`）。
- 触发链：Unity 受管异常路径 new `java/lang/Error` + `JNIEnv::Throw()`
  （`javastubs/javac.h` 的 `[BD]` 注释早就记着这条）→ `Throw()` 不填 `except`
  → 下一次 JNI 调用 rethrow 空指针 → SEGV。

## 本次改动（全部已编译验证）

| 文件 | 改动 |
|------|------|
| `platform/common/debug_utils.cpp/.h` | `segfault_handler` 改 **SA_SIGINFO**，打印 `si_code`/`si_addr`/`pc`/`lr`/`fp`/`sp`/全部 x0-x29，并用 `bd_describe_crash_address()` 解析成 `module+offset`；信号集扩到 SEGV/BUS/ILL/FPE/ABRT |
| `thunks/libc/misc.cpp` | `bd_dump_abort_backtrace`/`bd_scan_caller_frames` 的 `"BD-ABORT: "` 前缀参数化为 `tag`；导出 `bd_dump_crash_backtrace(tag)` 与 `bd_describe_crash_address(tag,label,addr)` 供 SEGV handler 复用 |
| `thunks/libc/fcntl.cpp` `stdio.cpp` | `open("")`/`fopen("")` 专门诊断（空路径返回 -1 前打 tag 并 dump 调用栈） |
| `libjnivm/include/jnivm/throwable.h` | 新增 `jnivm::RethrowThrowable()`：空 `except` 时抛 `std::runtime_error`，不碰 `rethrow_exception` |
| `libjnivm/include/jnivm/method.h` | `j2invoke` 只在 `except` 非空时 rethrow（Throw() 来的异常保持 pending，符合 Android 语义） |
| `libjnivm/src/jnivm/vm.cpp` | `Throw()` 保持 `except` 为空并注释原因；`ExceptionDescribe` 走 `RethrowThrowable()` |
| `projects/unityloader/javastubs/unity.cpp` | `= 0x%p` → `= %p`（消除 `0x0x`）；`getFieldID` 日志 `field` → `field.get()`（shared_ptr 过 varargs 是 UB） |

# 2026-09-21（第三场）— 查清「截图纯黑」：不是抓图时机问题，是**一帧都没 present**

## 问题

用户问"最终画面截图是什么样"，给出去的 `shot-fix2.png` 是黑屏。先排除误判：
4 张截图全部 **192 B、640×480、bitdepth=1、colortype=0**，解码后每行全 0 → 纯黑属实。

## 两层原因（都要说清楚）

1. **抓图时机**：`_harness/run-oddmar.sh` 在 `SECS-2` 抓（SECS=30 → 28 s），
   而 Unity **3.9 s 就退出了**。窗口早没了 → 抓到空的 root window。
   这层只说明"那张图没意义"，**不能推出画面是黑的**。
2. **真因**：Unity 全程**没 present 过一帧**。用新写的
   `_harness/run-oddmar-seq.sh`（存活期每 250 ms 抓一张 + `BD_DUMP_FRAME_AT=1`
   让 loader 自己 `glReadPixels` GL drawable）实测修复版：

```
帧序列   23/575/1114/1763/2294/2827/3357 ms → 每张 192 B 纯黑
窗口     18–1605 ms windows=0；2004 ms 起 windows=1，持续到退出
swap     无任何 .gl.ppm；eglSwapBuffers 调用次数 = 0
退出     exit=0 @ 3.9 s（[BD-EXIT] nativeRender returned false）
```

结论：SDL 窗口建起来了（640×480 GL 3.2 context、`eglMakeCurrent` 都有日志），
但 Unity 两次 `nativeRender` 都没走到 present，第二次直接返回 false 退出。
**"最终画面"就是纯黑——因为从来没有过一帧，不是画黑的。**
192 B 这个体积本身就是判据（单色 640×480 压完就这么大；有内容会到几十 kB）。

## 新增工具（已进 `_harness/`，并 docker cp 到容器 `/`）

- `run-oddmar-seq.sh` — 逐帧截图 + 时间线 + `xwininfo` + `BD_DUMP_FRAME` 三联证；
  产物在 `$SEQ_DIR`（默认 `/game/Oddmar/seq`）：`%04d.png` / `timeline.txt` /
  `xwininfo.txt` / `frame.*.gl.ppm`。**判据**：有 ppm 而截图黑 = 画了没 present；
  没 ppm = `eglSwapBuffers` 没被调用。
- `probe-oddmar-window.sh` — 存活期轮询 `xwininfo -root -children` 数子窗口，
  区分"窗口没建"与"窗口建了没内容"。注意 `grep -c '^     0x'` 数的是**子窗口数**
  （root 行是 `xwininfo: Window id: ...`，2 空格缩进的 `  Root window id:` 不会命中）。

## 两个坑

1. **`BOOT_LOADER` 有默认值** `/workspace/Bogodroid/build-oddmar/unityloader`。
   只重建 `build-oddmar-verbose` 却忘传 `BOOT_LOADER` → 跑的是老二进制，
   会看到"崩溃又回来了"的假象。判据：新 handler 打 `si_code`/`si_addr`/`pc`/`lr`；

2. 我的 bash 里 `date +%s%N` 与 `stat -c%s` 在容器内可用（Ubuntu 20.04 coreutils），

# 第二场（续）：present 打通了，画面仍黑 —— 卡点转到资源层

详细交接见 **`docs/HANDOFF-ODDMAR.md`**（新会话先读那份）。这里只记结论与新踩的坑。

## 状态跃迁

`eglSwapBuffers` 从 **0 → 14 次**，进程 32s 跑满无 CRASH，写出 `frame.{1,2,3}.gl.ppm`；
但三帧 **mean R/G/B = 0**，PNG 仍 192 B → **画的是空场景，不是没画**。
黑屏根因收敛：`com.mobge.assetlocator.AssetLocator.<init>` 仍 miss → 资源列表拿不到 → 场景未加载。
**卡点已从图形层转移到资源层。**

## 最大的时间黑洞：libjnivm 日志过滤器

`libjnivm/src/jnivm/internal/log.h` 的 `jnivm_log_enabled(tag, format)`：

- 看的是 **tag** 是否以 `"BD-"` 开头（**不是 format**）；
- 否则 format 需命中白名单 `STUB-MISS`/`Exception`/`Unknown`/` is null` 等。

→ 我写的 `LOG("JNIVM", "[BD-MISS] ...")` **全部被静默丢弃**，
导致我据此得出"没有 RegisterNatives 调用"的**错误结论**（实际有 8 个类、几十条）。
改 tag 为 `BD-REG`/`BD-JNIVM` 后真相立刻出现。
**规则：自定义诊断一律 `LOG("BD-XXX", ...)`；要看全部内部流量用 `BD_JNI_TRACE=1`。**

## 自己引入并修掉的一个 bug（教训）

把 `if(!isStatic && sname == "<init>")` 放宽成 `if(sname == "<init>")` 后，
我在**函数体内**又套了一层 `if (isVoidCtor)`，于是签名已是改写形态时
（static 重入那次）条件成立、内判为假，**既不 return 也跳过了 else 的查找代码**。
症状极具迷惑性：`[BD-MISS]` 打印的查找键与注册项**逐字节相同**却判 miss。
**教训：往"条件 + else"里塞内层判断，必须确认内层为假时控制流去哪。**

## 反直觉：`Constructor::newInstance` 从未被调用

Unity 拿到 `getConstructorID` 返回的 `Constructor` 对象后**不调 newInstance**，
直接当 jmethodID 调（走 jinvoke 的 static 分支）。
所以 `[STUB-MISS] Unknown Static` 里的 `Sig=` 是**被调用对象自己的签名**，
**不要当成"查找键"来推理** —— 我在这上面绕了很久。

## 遗留（给新会话）

1. **P0 回归**：本次改的是 `libjnivm` 核心（`GetMethodID` 的 `<init>` 改写不再区分 `isStatic` + 签名点号→斜杠归一化），
   **全局生效，会波及其他端口，必须先回归其他游戏**。
2. **P0 定位**：`AssetLocator` 被调用的 mid 签名是**点号 + `V`（未改写形态）**，
   却经过了 `Unknown Static` —— 需在 jinvoke static 分支打 `mid` 指针，
   与 `getConstructorID` dump 的注册项指针对照，查它是哪个对象。
3. **结构隐患**：`GetMethodID` miss 时无条件 `push_back` 空桩，
   而 `find_if` 只取**第一个**命中 → 首条 miss 的空桩会**永久遮蔽**后续同名同签名的注册项。
   建议改为"复用同名同签名条目并填充"。
4. 诊断日志清单见 HANDOFF §4.2，验证完应清理。

## 卡点定论（HANDOFF §6 P0 可以关掉了）

```
3370 [UnityReflection] getConstructorID(com/mobge/assetlocator/AssetLocator,
       (Lcom.unity3d.player.UnityPlayerActivity;Ljava/lang/String;)V) = 0x40030d3425f0
3369 [BD-CTOROBJ] ret=0x40030d3425f0 sigfield=0x40030d342668 text=(Lcom/unity3d/player/UnityPlayerActivity;Ljava/lang/String;)V
3372 [BD-MID] Unknown Static mid=0x40030d3425f0 name=<init> static=0 native=(nil) handle=(nil)
       sig=(Lcom/unity3d/player/UnityPlayerActivity;Ljava/lang/String;)V
```

**mid 指针 == `getConstructorID` 返回值**，`handle=(nil)`、`static=0`、`native=(nil)`。

根因链（三条都是代码事实）：

1. `libjnivm/src/jnivm/vm.cpp:466-469`：JNI 表里 `AllocObject` 之后连续三个槽是
   `MDispatch<jobject, jclass>::CallMethod` —— 即 **`NewObject`/`NewObjectV`/`NewObjectA`
   被实现成"对类做一次静态调用"**。
2. `libjnivm/src/jnivm/internal/method.cpp` 的 `MDispatchBase2<T>::CallMethod(JNIEnv*, jclass, jmethodID, jvalue*)`
   只有两条成功路径：`mid->dynamic` 与 `mid->nativehandle`；都没有 → `Unknown Static` → 返回默认值。
   所以**构造器 jmethodID 必须是已注册的那条 `FakeJni::Constructor` 条目（有 nativehandle）**。
3. `javac.h:22` `reflect::Constructor : public jnivm::Method`，而 `javac.cpp:59-71` 的构造器
   **只设 `name`/`signature`**，`nativehandle`/`dynamic`/`native` 恒空。
   → `ReflectionHelper::getConstructorID` 交出去的这个包装对象，**架构上永远构造不出东西**。

**旁证**：整轮日志里 `com/mobge/assetlocator/AssetLocator` **一条 `[BD-CTOR-ENTER]` 都没有**

## 第八场（续）：Oddmar 黑屏 —— 打通了两层启动阻塞（2026-09-21 晚）

### 结论：黑屏的第一个真根因找到了两处，且都已修好并实测推进

**修 1 — 未绑定构造器返回 null 对象（`projects/unityloader/javastubs/unity.cpp`）**
`ReflectionHelper::getConstructorID()` 在类没有绑定 `<init>` 时返回空包装 → `new AndroidJavaObject` 得 null
→ 托管侧把这个 null 当参数传给下一个 `AndroidJavaObject` → Unity 的
`_AndroidJNIHelper.GetSignature(obj)` 解引用 null → `NullReferenceException`。
Java 的 `new` 从不返回 null，所以改成**合成一个惰性活对象**（`ctor->dynamic` + `ToJNIType`）。
逃生开关：`BD_CTOR_FALLBACK_NULL=1` 恢复旧行为（A/B 用）。

**修 2 — 自造类没有继承链（`libjnivm/src/jnivm/internal/findclass.cpp`）**
`jnivm::GetMethodID()` 只沿 `cur->baseclasses` 走继承链，而 `InternalFindClass` 新造的类**没有 baseclasses**
→ `Object.getClass()/toString()/equals()` 全部 miss 返回 null → 同样砸在 Unity 的 `GetSignature` 上。
在 `InternalFindClass` **出口**统一补 `java/lang/Object` 父类（懒解析 + weak_ptr 缓存，跳过 `java/lang/Object` 自身）。

⚠️ **踩坑记录**：`JNIVM_ENABLE_DEBUG` 恒 ON ⇒ `JNI_DEBUG` 已定义 ⇒ `InternalFindClass` 走的是
**命名空间分支**（`#ifdef JNI_DEBUG` 里的那段），**根本不会**执行 `vm->classes.find()` 那个 fallback 分支。
第一次把修复写在 fallback 分支里，编译过了、跑起来毫无效果。**必须写在函数出口。**
另外 `#ifndef NDEBUG` 包着的 `[BD-PHANTOM]` 日志在 RelWithDebInfo/Release 下是编译掉的 —— 已改成常开。
`libjnivm/src/jnivm/vm.cpp` 的 `FindClass` 也加了 `[BD-FINDCLASS]`（guest 显式要类的入口）。
